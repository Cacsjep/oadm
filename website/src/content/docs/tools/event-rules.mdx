An event rule says: **when** this happens, **then** do that. For example: while a camera reports blur during working
hours, switch on the warning lamp on the I/O box and show an overlay on the camera.

<Image src={page} alt="The Event rules page with three rules" class="screen" />

<Aside>
Creating and changing rules needs the permission **Change event rules** (administrators have it). Operators see the rules
and the event log.
</Aside>

## Create a rule

<Steps>

1. Open **Event rules** in the navigation rail and click **New rule**. The rule is made in four steps; **Next** goes
   on once a step is complete.

2. **Rule**: enter a name. **Dead time** and **Max per minute** can stay as they are.

3. **When**: choose the event. The events sit in folders (Devices, Certificates, Sites, then one per plugin, such as
   Dashboards or Text recognition); type a few letters to search them. Then choose the devices with **Choose devices**:
   all devices, or any mix of tags and single devices. A tag also covers devices you tag later. Add more conditions if you need them. They all must hold:
   - **Add check**: a value of the event, for example Temperature > 40. See [Check the values](#check-the-values).
   - **Add event**: another event, on the same device or on any device you choose. Example: blur, and the camera is
     reachable.
   - **Add schedule**: weekdays and a time window. Example: Monday to Friday, 08:00 to 18:00.

4. **Then**: choose up to five actions. They run in the order of the list. With **Choose devices** pick where each one
   runs: on the device of the event, on all devices, or on tags and single devices.

5. **Overview**: check the rule and click **Save**.

</Steps>

## Events

| Event | Comes from |
|---|---|
| Device unreachable, Credentials required, Certificate changed | The device status OADM sees |
| Any device: unreachable, credentials required, certificate changed | On while at least one device has the status; the value `{count}` says how many. No device |
| Any device: clock off | On while at least one device clock differs from the OADM server by more than the allowed clock difference, or its NTP is not synced; `{count}` says how many. No device |
| Certificate expires soon, Certificate expired, and their Any device events (group Certificates) | The HTTPS certificate of the device, with the days of the **Expiry warning** policy on the [PKI](../pki/) page |
| Any event a device offers (inputs, virtual inputs, Object Analytics, Image Health Analytics, storage, ...) and its "connection lost" | [Device triggers](../device-triggers/) you create |
| Text read (group Text recognition, one per reader): Area, Text, Text read, All matches, Number, Confidence, Matches format | The readers of [Text recognition](../text-recognition/events/#event-text-read) |
| Reader problem (one per reader), Any reader problem | On while a text reader cannot read, see [Text recognition](../text-recognition/events/#event-reader-problem) |
| Optional plugin not loaded (group Optional plugins) | On while an optional plugin must be installed again; `{count}` and `{plugin}` |

Most events are on while something is true and off again when it ends. Then the rule is **on** while all conditions
hold, and some actions can undo themselves when the rule turns **off**.

## Check the values

Many events carry values, for example the temperature of a sensor or the state of a door. **Add check** below the event
compares one of them. The event counts only while all its checks hold, up to five per event.

| Value | Checks |
|---|---|
| Text | equals, does not equal, contains, starts with (upper and lower case do not matter) |
| Number | = equals, ≠ does not equal, > greater than, ≥ greater than or equal, < less than, ≤ less than or equal. Write decimals with a point: 21.5. For a range add two checks, Temperature ≥ 20 and Temperature < 30 |
| Yes or no | is yes, is no |

While the event is on, every new value is checked again: a temperature that rises above 40 turns the rule on, and when it
falls back the rule turns off. An event that does not send the value never passes the check.

## Actions

- **Set output**: switches an output of the device, for example a relay. **Follow the rule** keeps it active while the
  rule is on. **Pulse** switches it on for a number of seconds. **Set active**, **Set inactive** and **Toggle** do what
  they say.
- **Run VAPIX command**: sends a saved command of the [VAPIX Commander](../vapix-commander/), with its values and
  passwords. Optionally a second command when the rule turns off, for example to hide an overlay again. Commands marked
  dangerous need **Allow dangerous commands**. Text fields of the command take [placeholders](#placeholders).
- **Send HTTP request**: calls a web service, for example a webhook of Teams or Slack or a building system. Choose a
  [recipient](#recipients), then the method, query parameters, headers and a body as JSON, XML, text or form.
- **Send email**: sends a mail to a [recipient](#recipients), as text or HTML.
- **Publish MQTT message**: publishes a message to a topic on an MQTT broker, a [recipient](#recipients).
- **Write Modbus value**: writes on or off, a number or text to a PLC or gateway, a [recipient](#recipients). Addresses count from 0.
- **Write OPC UA value**: writes on or off, a number or text to a node of an OPC UA server, a [recipient](#recipients).
- **Send TCP message**: sends a message to a [recipient](#recipients), for example a building, alarm or video system that
  listens on a TCP port. Text, JSON, XML or hex bytes (`02 41 42 03`), with an optional line end. **Wait for an
  answer** with **Answer must contain** fails the action when the other side does not confirm.
- **Log entry**: writes a message to the server log (**Logs** page, **Server**) and does nothing else. Good for testing
  a rule.
- **Read text**: reads one picture with a reader of [Text recognition](../text-recognition/events/#action-read-text) now
  and sends its **Text read** and **No text read** events. No devices to choose: the reader names its camera.

Email, HTTP and TCP run once each time the rule turns on or fires. Check **Also send when the rule turns off** for a second
message when it ends; `{state}` tells which one it is.

### Placeholders

Every text of an action can hold placeholders that OADM fills in when the rule runs: the rule, the event, the device
(address, host name, model, serial number, MAC address, AXIS OS, tags, a link to its web interface) and every value of the
event, for example `{objectId}`. The **Placeholders** card next to the actions lists them; the icon copies one.

In a JSON, XML or HTML body and in a JSON or XML TCP message OADM escapes each value, so `"objectID": "{objectId}"`
stays valid whatever the event sends. Text sends the values as they are.

**Send test** sends the email, the request or the message once right away, with sample values for the event and the
first device of the trigger. For MQTT, Modbus and OPC UA it is off: use **Test** on the recipient, which only connects.

When several devices turn a rule on, an action on chosen devices (the lamp on the I/O box) switches on with the first
one and off when the last one ends.

## Recipients

A recipient says where to send, the action says what to send. Like the recipients of an Axis device, except that a rule keeps a
link: change a recipient and all its rules follow.

The **Recipients** card sits next to the rules. **New** asks for the type, a name and the type's fields:

| Type | Holds |
|---|---|
| HTTP | URL, **Login** (Basic, Digest or Bearer token), **Allow untrusted certificates** |
| Email | Mail server, port, encryption, **Allow untrusted certificates**, user name, password, From, To |
| TCP | Host, port, **Use TLS**, **Allow untrusted certificates** |

**Test** sends once now and shows the reason when it fails. Leave a stored password empty to keep it. A target takes no
[placeholders](#placeholders). For a second audience, create a second recipient.

In a rule, choose the recipient in the action, or click **New** next to the select.

**Delete** is refused while a rule uses the recipient: the message names the rules to change first.

:::note[Rules from older versions]
OADM does not move these rules for you. A Send email, Send HTTP request or Send TCP message of an older rule shows **Choose a
recipient.**, does not run, and the event log says so. Create the recipient, open the rule and choose it. The old server settings
go when you save the rule.
:::

### MQTT, Modbus and OPC UA

An MQTT, Modbus or OPC UA recipient keeps one connection open, which all its rules share. It connects at the first action and closes after 5 minutes
without one. The icon in the list shows the state, the tooltip the reason. **Test** only connects, it sends nothing.

A new recipient needs only its address. TLS for MQTT, and security and login for OPC UA, are there when you need them. Certificates come from the
[PKI](/tools/pki/) page: import or create one there, then choose it in the recipient. OPC UA with security needs a certificate imported into PKI.

An action never waits for a connection that is down: it fails, and the event log says why. Nothing is sent later. Use the event
**Recipient not connected** to act on it.

## Manage rules

- Turn a rule on or off with its check box. Turning off a rule that is on runs its "turn off" actions, so a lamp does
  not stay on.
- **Duplicate** copies a rule, turned off, with its stored passwords.
- **Delete** removes a rule after a confirmation.
- The **State** column shows whether a rule is on and for how many devices, and when an event or action is not available
  because its plugin is turned off.

## Event log

The **Event log** below the rules and recipients lists what happened: the events your rules use, when a rule turned on, off or ran, and every
action with its result. The newest entries come first and new ones appear live. OADM keeps the log for 30 days or
100,000 entries. Administrators can empty it with **Delete all**.

## Good to know

- **Dead time** (default 10 s): after the rule ran for a device, that device is ignored for this long. **Max per
  minute** (default 60 runs per minute for the whole rule): further events are skipped. Both protect against a flickering
  camera; skipped runs are noted in the event log.
- After a server restart OADM checks every event again and runs only what changed while it was down.
- A failed action is logged; the next action of the rule still runs. OADM does not retry.
- Devices that need a login, have no password yet or have a changed certificate are skipped.
